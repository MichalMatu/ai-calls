## Findings (risk-ordered)

### P0 / AUDIT-01 — Negative Orange response is accepted as CLIR success

Evidence: [ChatRelayLiveCallProbe.kt lines 519–525](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/developerrelay/ChatRelayLiveCallProbe.kt#L519-L525) accepts any transcript containing `włączon`, `aktyw`, `uruchom`, etc. [lines 275–278](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/developerrelay/ChatRelayLiveCallProbe.kt#L275-L278) promote this to `pendingExternalSuccessEvidence` after permit consumption, and [lines 417–419, 477–505](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/developerrelay/ChatRelayLiveCallProbe.kt#L417-L505) complete the external effect/workflow.

**Reproduced:** exact production predicate transcribed into a standalone Kotlin/JVM harness and executed with `kotlinc 1.9.0`. It returns `true` for all four *failure* transcripts:
- `Usługa CLIR nie została włączona`;
- `Nie udało się aktywować usługi CLIR`;
- `Usługa CLIR jest nieaktywna`;
- `Nie możemy uruchomić usługi CLIR`.

Expected: none of these may yield factual success. Impact: app can mark `SET_SERVICE(CLIR=true)` as completed when the carrier explicitly says it failed. The matcher also does not tie the positive phrase to CLIR rather than some unrelated service.

Remediation: replace keyword-only success with **typed, CLIR-specific positive/negative evidence validation**; fail closed on ambiguity/negation, preserve only redacted evidence. A permissive `contains` check is not enough; add table-driven Kotlin tests covering genuine success, negation, unrelated service activation, ambiguous prompts, partial STT, Polish morphology and contradictory statements. Independent network-state verification must remain a separate acceptance gate.

### P0 / AUDIT-02 — No proof that the call being ended belongs to the campaign

Evidence: [AppOwnedClirCampaignExecutor.kt](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/campaign/AppOwnedClirCampaignExecutor.kt). Before dial, code checks only `TelecomManager.isInCall`; after `ACTION_CALL`, `waitForActiveCall` checks `AudioManager.MODE_IN_CALL`. In `endOwnedCall`, when **any** call is active it calls `TelecomManager.endCall()`. No stable call/subscription identity or ownership handle is checked. The same function is used on activation timeout and runtime completion.

**Source-established race:** if the intended call ends and an unrelated call becomes active before timeout/cleanup, this code may end the unrelated call. The runtime may also attach to a call that happens to become active after the dial intent, without proving it is the requested `*100` call. This violates `docs/SECURITY_PRIVACY.md`'s rule not to terminate unrelated calls.

Remediation: introduce an application-owned concrete call lifecycle identity/ownership binding, checked before media start and cleanup. Where the platform cannot identify the exact owned call, fail closed and do **not** invoke generic `endCall()`. Cover IDLE→owned ACTIVE→IDLE, dial failure, delayed activation, unrelated incoming/outgoing calls, call replacement and cleanup races. Requires on-device validation; do not alter the frozen Samsung media/helper layer without a proven root cause.

### P1 / AUDIT-03 — Grant revocation is not checked again at external commitment

Evidence: [AppOwnedClirCampaignExecutor.kt](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/campaign/AppOwnedClirCampaignExecutor.kt) authorizes/reserves a grant only before dial and sends a Boolean `phoneDisclosureAuthorized` into the live runtime. [ChatRelayLiveCallProbe.kt lines 458–475](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/developerrelay/ChatRelayLiveCallProbe.kt#L458-L475) consumes a commitment permit using route/effect checks but **does not re-check campaign grant state, revocation, expiration or account scope**. [CampaignToolActivity.kt](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/campaign/CampaignToolActivity.kt) exposes a revoke control while a call may be active.

Scenario: revoke a grant during a connected call, then the existing dialogue reaches commitment or PHONE disclosure. The earlier authorization snapshot is still used. Whether revocation is contractually intended to stop in-flight sessions needs a precise documented policy; current code does not enforce prompt revocation for these future actions.

Remediation: persist/validate a grant generation/session authority token and check live revocation/scope before each external commitment and before plaintext disclosure; cancel/close the owned call safely on revocation. Test revoke-during-call and revoke-between-approval-and-speech, no additional dial.

### P1 / AUDIT-04 — Grant read-modify-write is only locked per store instance

Evidence: [CampaignAuthorizationStore.kt](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/campaign/CampaignAuthorizationStore.kt) uses `@Synchronized` on instance methods `load`, `reserveAttempt`, `save`, `revoke`. [CampaignToolActivity.kt](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/campaign/CampaignToolActivity.kt) and [AppOwnedCampaignService.kt](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/campaign/AppOwnedCampaignService.kt) independently construct store instances, backed by the same shared preferences.

Risk: two concurrent read→modify→write transactions need not serialize across store instances. A stale reserve operation may overwrite revocation or attempt counts. `SharedPreferences.Editor.commit()` persisting each write does not turn the full read-modify-write into one cross-instance transaction.

Remediation: one application-level shared lock/actor for every grant mutation, or transactional persistent storage, plus explicit atomic reserve-and-authorize with expiry/revocation/account revalidation. Regression: deterministic interleavings of simultaneous reserve, revoke, reauthorize and exhausted attempts.

### P1 / AUDIT-05 — Workflow success is set before independent network verification

Evidence: [ChatRelayLiveCallProbe.kt lines 477–509](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/developerrelay/ChatRelayLiveCallProbe.kt#L477-L509) calls `workflow.complete(SUCCESS)` based on textual evidence before independent `*#31#` verification. [AppOwnedClirCampaignExecutor.kt](https://github.com/MichalMatu/ai-calls/blob/e950c42c26cb34452317e551b73aee2198baf85d/app/src/main/kotlin/pl/michalmatu/aicallbridge/campaign/AppOwnedClirCampaignExecutor.kt) correctly warns in UI that network verification remains required. `README.md`, `docs/ROADMAP.md`, and `docs/SECURITY_PRIVACY.md` require independent network verification for CLIR acceptance.

Remediation: model an explicitly provisional `carrier_reported_success` state distinct from `verified_external_success`; do not set a terminal verified-success state until separate independent evidence is recorded. Tests must distinguish permit consumption, carrier reported state and verified network state.
