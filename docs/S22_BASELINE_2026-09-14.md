# Galaxy S22+ capability baseline — 2026-09-14

This is the durable Phase 0.5 evidence snapshot collected from the physical target phone before a dedicated test SIM was available.

It records what was actually reproduced on the device and separates that from the live-call work that still requires a second number/SIM.

## Target tuple

- Manufacturer: Samsung
- Model: `SM-S906B` (Galaxy S22+)
- Product/device: `g0sxeea` / `g0s`
- Android: 16
- API level: 36
- One UI system property: `80000` (One UI 8.0 on this build)
- Build display: `BP2A.250605.031.A3.S906BXXSOGZH3`
- Build fingerprint: `samsung/g0sxeea/g0s:16/BP2A.250605.031.A3/S906BXXSOGZH3:user/release-keys`
- App package: `pl.michalmatu.aicallbridge`
- Probe code was built from `main` during the 2026-09-14 Local Agent session.

Do not publish or store device serial numbers, IMEI, subscriber identifiers, phone numbers, ADB keys, or call recordings in this document.

## Normal application process

The user granted `RECORD_AUDIO`. Android reported:

```text
android.permission.RECORD_AUDIO: granted=true
```

The normal application process saw:

```text
audio_mode=NORMAL(0)
output_sample_rate=48000
output_frames_per_buffer=192
communication_device=BUILTIN_EARPIECE
available communication devices=BUILTIN_EARPIECE, BUILTIN_SPEAKER
```

The full device inventory contained seven audio devices, including:

```text
TYPE_TELEPHONY sink   id=11
TYPE_TELEPHONY source id=17
REMOTE_SUBMIX source  id=21
```

Important result: stock Samsung firmware exposes both telephony directions as `AudioDeviceInfo.TYPE_TELEPHONY` devices to the normal process.

Normal-process `AudioRecord` construction behaved as expected for an ordinary app:

```text
MIC                 initialized
VOICE_COMMUNICATION initialized
VOICE_RECOGNITION   initialized
VOICE_CALL          UnsupportedOperationException: Cannot create AudioRecord
VOICE_DOWNLINK      UnsupportedOperationException: Cannot create AudioRecord
VOICE_UPLINK        UnsupportedOperationException: Cannot create AudioRecord
```

This is evidence that the normal APK is not the correct execution boundary for direct cellular call capture.

## ADB shell / future Shizuku-equivalent privilege level

The shell probe executed as:

```text
uid=2000(shell)
SELinux context=u:r:shell:s0
```

At this privilege level the probe confirmed that the following permissions are granted to the shell identity on this firmware:

```text
android.permission.CAPTURE_AUDIO_OUTPUT = granted
android.permission.MODIFY_AUDIO_ROUTING = granted
android.permission.MODIFY_PHONE_STATE   = granted
```

This does **not** prove that every API guarded by these permissions will work. UID checks, service checks, SELinux, call state and vendor audio policy can still block individual operations.

## Shell capture-source initialization

With no active cellular call, UID 2000 successfully created initialized `AudioRecord` objects for all three call-specific sources:

```text
VOICE_CALL     state=INITIALIZED
VOICE_DOWNLINK state=INITIALIZED
VOICE_UPLINK   state=INITIALIZED
```

This is a major positive result for Phase 1A, but it is only `AVAILABLE_UNPROVEN`.

What is **not** proven yet:

- that `startRecording()` succeeds during a carrier call;
- that `VOICE_DOWNLINK` produces non-silent PCM;
- that the PCM contains the remote party rather than another mix;
- route behavior for earpiece/speaker/screen-off/VoLTE/Wi-Fi Calling.

Those items require the physical two-phone test.

## Shell telephony output observations

The shell process also saw both telephony devices:

```text
telephony sink   id=11
telephony source id=17
```

Two `AudioTrack` construction attempts were made while **no cellular call was active**:

```text
USAGE_MEDIA / MUSIC                  -> UnsupportedOperationException: Cannot create AudioTrack
USAGE_VOICE_COMMUNICATION / SPEECH   -> UnsupportedOperationException: Cannot create AudioTrack
```

This is **not** a Phase 1B failure verdict. The dedicated cellular/telephony output may only be openable while Android AudioPolicy has an active in-call route. The next injection test must therefore run during a real call.

## External precedent discovered during audit

`sidinsearch/AgentCall` independently demonstrates both telephony directions on a rooted/privileged Xiaomi POCO M2 Pro reference configuration:

- downlink capture with `VOICE_DOWNLINK` routed to the telephony RX device;
- uplink injection with `AudioTrack`, `USAGE_MEDIA`, and explicit `TYPE_TELEPHONY` TX routing;
- physical remote-party confirmation is used as the proof gate.

That project is useful architectural evidence, not proof for this S22+ and not a code source for this repository. It is AGPL-3.0; do not copy its implementation into this project unless the licensing consequence is intentionally accepted.

The `USAGE_MEDIA -> TYPE_TELEPHONY` route is now the first Phase 1B live-call candidate. `USAGE_VOICE_COMMUNICATION` remains a comparison path because BCP uses that style on some devices.

## Shizuku status

The successful results above were obtained through direct ADB shell execution (`app_process`) to measure UID 2000 capability with minimal moving parts.

This proves the **shell privilege class** needed by the planned helper, but it does not yet prove:

- Shizuku is installed/running on the target user;
- the app has Shizuku authorization;
- a Shizuku UserService reproduces the same behavior end-to-end.

That integration work remains separate from the underlying capability result.

## Pause point

Development is intentionally paused before the live media proof until a dedicated SIM/number is available for the S22+.

When the SIM is available, resume from:

1. active-call `VOICE_DOWNLINK` bounded capture;
2. inspect PCM and prove remote-only speech;
3. active-call `USAGE_MEDIA -> TYPE_TELEPHONY` deterministic tone injection;
4. if needed, compare `USAGE_VOICE_COMMUNICATION`;
5. only after both directions pass, begin the stable local bridge.

The executable handoff is maintained in `docs/superpowers/plans/2026-09-14-phase1-live-call-validation.md`.
