# Galaxy S22+ live-call evidence — 2026-09-15

This document records the first real carrier-call media measurements on the physical target phone. It supplements `S22_BASELINE_2026-09-14.md` and deliberately separates measured facts from unresolved source-direction and injection questions.

## Target and transport

- Device: Samsung Galaxy S22+ `SM-S906B` / `g0s`.
- Android: 16 / API 36.
- Build fingerprint remained `samsung/g0sxeea/g0s:16/BP2A.250605.031.A3/S906BXXSOGZH3:user/release-keys`.
- SIM: Orange PL, voice service registered and available.
- Development transport: paired ADB over Wi-Fi. The shell probe still executed as UID 2000; Wi-Fi vs USB did not change the Android shell privilege boundary.
- Test call: real outbound carrier call to an Orange automated voice service.
- No raw call audio was committed to Git.

## Active-call state

During the call Android reported:

```text
mCallState=2
AudioManager mode=2 (IN_CALL)
```

The shell inventory still exposed:

```text
TYPE_TELEPHONY sink   id=11
TYPE_TELEPHONY source id=17
VOICE_CALL            initialized
VOICE_DOWNLINK        initialized
VOICE_UPLINK          initialized
```

## Phase 1A — live digital downlink signal

A bounded one-off `VOICE_DOWNLINK` capture ran while `mCallState=2` before and after the read.

Format:

```text
sample rate: 16000 Hz
channels: mono
encoding: PCM16
requested duration: 2000 ms
```

Measured result:

```text
samples_read=32000
bytes_read=64000
non_zero_samples=30615
peak=15370
rms=2338.813069399466
read_errors=0
```

This proves that `VOICE_DOWNLINK` can start and return a strong non-silent digital signal during a real carrier call on this exact S22+ build.

A later repeatable project probe was added and run off-call as a control. With no call active it read the same telephony source but produced only near-silence:

```text
samples_read=16000
bytes_read=32000
peak=10
rms=1.8538473507816118
read_errors=0
```

The live/off-call contrast strongly supports that the live signal is call media rather than the ordinary idle floor.

### Autonomous signal-gated repeat

The bounded call runner was then validated end to end without manual phone interaction. It dialed the IVR, waited for `OFFHOOK`, and deliberately refused to treat call state as proof that remote speech had started.

The first three 250 ms downlink probes were true silence:

```text
probe 1: rms=0.000 peak=0 non_zero=0 read_errors=0
probe 2: rms=0.000 peak=0 non_zero=0 read_errors=0
probe 3: rms=0.000 peak=0 non_zero=0 read_errors=0
```

The fourth probe detected the remote audio onset:

```text
probe 4: rms=4884.364 peak=21090 non_zero=3928 read_errors=0
```

Only after that threshold crossing did the runner capture a 3 second diagnostic WAV:

```text
capture_source=VOICE_DOWNLINK
sample_rate=16000
duration_ms=3000
target_samples=48000
record_state=1
recording_state=3
routed_device=id:17,type:18,product:SM-S906B
samples_read=48000
bytes_read=96000
non_zero_samples=46062
peak=20054
rms=2376.92111045641
read_errors=0
```

The host file was 96,044 bytes: 96,000 bytes of PCM16 plus a 44 byte WAV header. The runner requested hangup from its fail-safe path and confirmed `IDLE` afterwards.

This validates the developer-control sequence:

```text
IDLE -> dial -> OFFHOOK -> wait for real downlink energy -> bounded capture -> hangup -> IDLE
```

### Classification

`LIVE DIGITAL SIGNAL PROVEN / SOURCE DIRECTION CONFIRMATION PENDING`

Do **not** promote Phase 1A to the repository's full media-direction `PROVEN_S22` level yet. The captures prove a strong remote-call-correlated digital signal, but the strict project gate still requires content-level confirmation that the stream contains the remote IVR specifically and excludes an unexpected local mix. A local transcription path is being added for that final classification.

## Phase 1B — generic telephony TX during an active call

While the same real call was active, the shell probe attempted both existing generic `AudioTrack -> TYPE_TELEPHONY` construction paths:

```text
USAGE_MEDIA / CONTENT_TYPE_MUSIC
  -> UnsupportedOperationException: Cannot create AudioTrack

USAGE_VOICE_COMMUNICATION / CONTENT_TYPE_SPEECH
  -> UnsupportedOperationException: Cannot create AudioTrack
```

This is materially stronger evidence than the 2026-09-14 off-call result because Android was in an active cellular call and `AudioManager` was in `IN_CALL` mode.

No PCM could be written because construction itself failed, therefore there was no remote audible-injection observation to perform.

### Classification

`FAILED_S22 CONSTRUCTION FOR CURRENT GENERIC CANDIDATES`

This does not prove that every stock-Samsung injection mechanism is blocked. It does satisfy the roadmap trigger for a focused Phase 1C Samsung-specific injection investigation while preserving the generic failure evidence.

## Repeatable tooling added after the call

The one-off downlink experiment has been converted into bounded project tooling:

```text
ShellAudioProbe inventory
ShellAudioProbe capture-downlink <durationMs>
ShellAudioProbe capture-downlink <durationMs> /data/local/tmp/<file>.pcm
scripts/s22_call_control.py
scripts/autonomous_call_loop.py
```

Properties:

- duration is bounded to at most 5 seconds;
- default capture is metrics-only and records no audio file;
- raw PCM output requires an explicit `/data/local/tmp/*.pcm` path;
- temporary phone-side PCM is deleted after pull;
- the host helper wraps PCM as 16 kHz mono PCM16 WAV;
- the signal-gated runner waits for real downlink energy rather than merely `OFFHOOK`;
- the runner refuses to start if another call is already active;
- after initiating a call it requests hangup from a `finally` path;
- the test helper can control call state, dialing, DTMF UI taps and hangup over ADB without replacing the default dialer.

## Next physical gate
